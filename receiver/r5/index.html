      How to interpret a lost reply

      A durable ledger row and an acknowledged caller response are separate facts. In ten two-event cases, the ledger contains the one expected paper order while the caller has no verified receipt; the safe caller result is unknown, so recovery must reuse the idempotency key or reconcile state. The archived replyUnconfirmed field means a response-loss event was observed, including cases that later recovered. New campaign records separate responseLossObserved from the final caller replyUnconfirmed state. A generic invariant_failure execution grade in these traces is not a ledger invariant violation: the final ledger checker passed with zero violations. The Q1 report keeps those outcomes separate.

      Audit scope and provenance

      The read-only audit recomputed seed and schedule counts, event application, summary outcomes, paired controls, final SQLite order/idempotency rows, execution-audit rows, revocations, and database integrity. The two-event bundle has no archived source snapshot and its recorded hashes match only 3/6 files in the current tree; an earlier clean-scratch verifier replay reproduced its aggregates and ledger outcomes but also recorded a one-file historical-source mismatch. Triple- and quad-fault bundles contain complete six-file snapshots matching their pinned digests. All campaigns use authored deterministic schedules, synthetic proposals, loopback services, one host, and a local SQLite paper ledger; they are not model-robustness, Futu, remote-network, or production-capacity results.

      Single policy host · 32 concurrent proposals

      One policy/orchestrator process routes 32 logical clients through one shared runtime, six service workers and one SQLite ledger. It exits after the durable commit but before returning the batch result; the same 32 proposal IDs then retry against the ledger.

      This fixed 32-client scenario is available on demand. It makes no model or external service calls.

      Grant one bounded action

      Ed25519 grants bind task, request digest, service audience, operation, resource, policy version, constraints and expiry. The model never holds the signing key.

      Keep data and authority separate

      Services verify a grant before dispatch and sign a receipt afterward. Results keep source and taint labels; content cannot mint the next grant.

      Make retries safe at the sink

      Risk and approval receipts bind the order hash. The synthetic ledger uses stable idempotency and signed recovery; redelivery causes one state transition.

      Scale boundary

      This demo exercises six independent service workers on one host. The local profile uses separate child processes over loopback; the Compose profile isolates each worker in a container on a private Docker network. Both use host-local SQLite for shared synthetic state. Local synthetic load results are not Futu topology or capacity evidence. A production deployment would add authenticated workload identity and mTLS, managed key rotation, durable cross-host policy and account state, atomic shared capacity reservations, fault-tolerant queues, regional consistency rules, and load-tested latency and error budgets. OrderGuard focuses on how agent intent and tainted data constrain authority as those services scale independently.
